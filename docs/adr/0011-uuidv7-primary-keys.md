# 0011. UUIDv7 primary keys

## Status

Accepted

Supersedes the identity-column PK rule in [ADR 0002](0002-single-postgres-database.md).
The rest of ADR 0002 (single Postgres, FKs, constraints, nixpkgs extensions) stands.

## Context

Domain tables used `bigint GENERATED BY DEFAULT AS IDENTITY`. That is a **central
allocator**: a row cannot exist until the database issues the next value.

Companion apps and offline capture need to mint tasks (and later projects, tags,
occurrences) without a round-trip. A second “client id” mapped onto a server bigint
is how these apps get messy.

UUIDv4 is globally unique but random, so PK B-trees scatter on insert. UUIDv7 is
time-ordered (RFC 9562) and unique, so insert locality stays close to identity.

This project already runs **PostgreSQL 18**, which has native `uuidv7()` — no
extension, no extra Nix package.

No production data yet, so the schema is rewritten in the original create
migrations rather than converted.

## Decision

### Domain keys

Every **domain** table uses a native `uuid` primary key with
`DEFAULT uuidv7()`:

- Current: `users`, `sessions`, `tasks`, `projects`, `project_folders`
- Future: tags, recurrences, folder memberships, and other product tables

Include users and sessions. Mixed `bigint`/`uuid` FKs forever is worse than
UUIDs on server-created rows. The invariant is: **domain entity keys are
UUIDv7 by default**, except occurrence ids that the recurrence rule itself
creates, which are a deterministic UUIDv5 ([ADR 0014](0014-offline-sync.md)).

UUIDv7 is the default, not a ban on other types. A column that is not a
client-mintable entity key uses whatever fits. A server-only monotonic counter
is `bigint GENERATED … AS IDENTITY`, not `serial` and not an explicit
sequence. The change-feed cursor is `GENERATED ALWAYS AS IDENTITY`
([ADR 0014](0014-offline-sync.md)).

Leave Rails internals alone (`schema_migrations`, `ar_internal_metadata`, Solid
Cache / Queue / Cable).

### Generation

- **Database default** `uuidv7()` for server `INSERT`s that omit `id`.
- **Explicit ids are allowed** (a `DEFAULT`, not `GENERATED ALWAYS`). Offline
  clients, fixtures, and `pg_restore` may supply their own.
- Apps may also mint with `SecureRandom.uuid_v7` (Ruby 3.3+) when the id is
  needed before insert. Either source is valid.
- Store `uuid`, never `text` / `varchar` UUIDs.
- Do **not** use UUIDv4 (`gen_random_uuid()`) for new keys.

### Join tables

HABTM-style rows (task↔tag, later memberships) get **their own** UUID PK plus a
unique pair on the two FKs. Sync wants an identity for the membership, not only
for the two ends.

### Not a capability token

UUIDs are identifiers, not secrets. Still scope by `current_user` / future folder
membership (ADR 0003). Do not treat an unguessable URL as authorization.

### Not a clock

Client clocks can be wrong, and fixtures (Rails uses UUIDv5 for labeled rows)
will not sort with server-minted v7 ids. Do not use `order(:id)` / `Model.last`
for recency. `ApplicationRecord` sets `implicit_order_column = "created_at"`.
Keep `created_at` as the display clock; `id` is only a tiebreaker
(`recent_first` today).

### Not the whole sync protocol

This only removes the ID-allocation blocker. Field patches, the change feed,
tombstones, ranks, and conflict rules are [ADR 0014](0014-offline-sync.md).
That ADR also makes the one exception to “new domain keys are v7”: recurrence
occurrences the rule itself creates use a deterministic UUIDv5.

## Consequences

- Production Postgres must be **18+** (`uuidv7()`). Local devenv already is.
- Migrations: `create_table :name, id: { type: :uuid, default: -> { "uuidv7()" } }`
  and `t.references :other, type: :uuid, foreign_key: true`.
- Rails generators default to `primary_key_type: :uuid`; the PostgreSQL adapter
  PK DDL is overridden so we do not fall back to identity / `gen_random_uuid()`.
- URLs are longer (`/tasks/0193…`). Fine.
- Index keys are 16 bytes instead of 8. Irrelevant at this scale.
- `structure.sql` stays the schema dump (enums + `uuid` defaults).
- Do not reintroduce identity/`serial` surrogate keys on domain entity tables.
  Identity columns elsewhere are fine when the value must come from the server.
- Do not add a parallel `client_uuid` beside a bigint PK.
